하네스 엔지니어링과 자가 진화 에이전트

모델 가중치는 고정한 채, 모델을 둘러싼 하네스(컨텍스트 · 워크플로우 · 메모리 · 서브에이전트 · 평가)를 설계하고 자동으로 진화시키는 방법을 배웁니다. 그리고 그렇게 올라간 점수가 정말 똑똑해진 것(G)인지, 벤치마크 암기(O)인지, 돈을 더 쓴 것(T)인지 분해해서 검증하는 법까지.

AI의 "뇌"는 그대로 두고, 뇌에 붙은 손·눈·수첩·규칙집을 더 잘 짜서 일을 잘하게 만드는 방법이에요. 그리고 성적이 올랐을 때 "진짜 실력이 늘었나, 답지를 외웠나, 시험을 여러 번 봤나"를 가려내는 법도 배워요.

1. 한눈에 보기

이번 수업은 Week 5-1 "Introduction" 파트만 다룹니다. 목차의 Reflexion · Voyager · A-MEM · R-Zero · Range-GRPO · Evo-Bench 등은 다음 수업 범위로 보입니다. 요약본에 빠진 STOP 경고 결과, AHE 관측가능성 3기둥, 진화 탐색 계보, 자동 연구 6가지 실패 모드, Anthropic 평가 가이드(p.67~92)를 이 페이지에 모두 넣었습니다.

2. 핵심 개념

CONCEPT 01 · p.10–14, 19

하네스(Harness)와 재귀적 자기개선(RSI)

하네스는 베이스 모델을 둘러싸고 실행을 오케스트레이션하는 시스템입니다. 모델이 어떻게 생각·계획하고, 어떤 툴을 호출해 행동하고, 컨텍스트를 어떻게 관리하고, 산출물을 어디에 저장하고, 결과를 어떻게 평가할지를 결정합니다. RSI는 I. J. Good(1965)의 "ultraintelligent machine"에서 시작해 Yudkowsky(2008)가 "AI가 자기 지능을 만드는 인지 기계장치를 스스로 개선하는 피드백 루프"로 정의했습니다. 현대적 해석에서 이 루프는 (1) 가중치 직접 수정, (2) 학습 파이프라인 개선, (3) 배포 시스템 개선을 포함하고, 배포 시스템 = 하네스 + API/서빙 + 인프라 + 모니터링 + 보안입니다. 초기 프레임워크의 agent = LLM + memory + tools + planning보다 훨씬 넓어서, 하네스 엔지니어링은 "프롬프트 템플릿"이 아니라 "런타임 소프트웨어 설계"에 가깝습니다.

이 사이트도 하나의 하네스입니다. 학습자(모델)는 그대로 두고 공부라는 작업의 루프(개념 → 조작 → 비교 → 문제)를 바꿨습니다.

모델이 "뇌"라면 하네스는 뇌에 붙은 손·눈·수첩·규칙집이에요. 뇌는 그대로 두고 수첩을 어떻게 쓰고 언제 손을 움직일지 규칙을 더 잘 짜면, 같은 뇌로도 훨씬 일을 잘해요. "스스로 더 좋아지는 AI"는 처음엔 뇌를 고치는 게 아니라 이 수첩과 규칙집을 스스로 고치는 것부터 시작해요. 이 사이트도 여러분의 뇌는 그대로 두고 "공부하는 순서"만 바꾼 하네스예요.

CONCEPT 02 · p.15–18

하네스 디자인 패턴 3가지

요약본의 "groom.me, grill with bug" 같은 명령 이름은 슬라이드 텍스트에 없습니다. 슬라이드의 패턴은 "File System as Persistent Memory"와 코딩 에이전트(Claude Code · Codex · OpenCode · Cursor) 사례입니다. 교수님 구두 설명이나 Claude Code 스킬 데모(예: /grill-me)였을 가능성이 있으니 발표 전 확인이 필요합니다 (p.16~18).

① 워크플로우 자동화: plan → execute → observe/test → improve → execute 루프를 모델이 돌 수 있게 정의합니다. 모델이 자기 궤적과 실패를 분석해 "agent runtime" 안에서 반복합니다(Karpathy의 autoresearch가 깔끔한 예). ② 파일시스템을 영속 메모리로: 전체 로그를 컨텍스트에 싣지 않고 파일에 durable state를 둡니다. 실험 로그·코드 diff·에러 트레이스는 컨텍스트 길이를 훨씬 넘기고, 파일 읽기/쓰기는 LLM의 기초 능력이라 모델이 좋아질수록 같이 좋아집니다. ③ 서브에이전트와 백엔드 잡: 여러 가설을 병렬로 탐색하고 부모 에이전트는 프로세스 매니저(launch / inspect logs / cancel / merge) 역할을 합니다. 핵심은 병렬성을 명시적이고 검사 가능하게 만드는 것. 서브에이전트 출력이 채팅 컨텍스트에만 있으면 사라지므로 파일·로그·상태 레코드로 남겨야 중단 후 복구와 이력 추적이 됩니다.

① 숙제를 "풀고 → 채점하고 → 틀린 거 고치고 → 다시 풀기"를 자동으로 반복하는 규칙. ② 머릿속에 다 외우려 하지 말고 공책(파일)에 적어두기. ③ 친구 셋에게 다른 방법을 동시에 시켜보되, 각자 결과를 종이에 적어 내게 해야 나중에 누가 왜 틀렸는지 알 수 있어요.

CONCEPT 03 · p.12, 20, 30

하네스 최적화의 진행 방향과 5가지 축

최적화 대상은 instruction prompts → structured context → workflow → harness code → optimizer code 순으로 깊어집니다. 축은 다섯 가지입니다. ① Context Engineering(모델이 받는 정보의 내용·구조·관리), ② Workflow Design(계획·실행·협조 방식), ③ Self-Improving Harness(에이전트가 자기 실행 시스템을 반복 개선), ④ Evolutionary Search(후보 생성·평가·선택), ⑤ Joint Optimization with Model Weights(파라미터와 하네스 동시 최적화). 하네스는 코드이므로, LLM이 코드를 최적화할 수 있으면 손으로 쓴 프롬프트보다 훨씬 큰 설계 공간에 접근합니다.

처음엔 "질문을 잘 쓰는 법"만 고치다가, 다음엔 "참고 자료 정리법", 그다음엔 "일하는 순서", 그다음엔 "일하는 순서를 짜는 프로그램", 결국엔 "그 프로그램을 고치는 프로그램"까지 고치게 돼요.

CONCEPT 04 · p.21–23

ACE (Agentic Context Engineering): 플레이북과 델타 업데이트

요약본의 "Qwen의 결과물을 상위 모델(GPT)이 평가 … Git 방식"에서, Qwen/GPT 역할 분담은 슬라이드 텍스트에 없습니다(그림일 수 있어 확인 필요). ACE의 구조는 Generator → Reflector → Curator이고, "Git 방식"은 델타 업데이트에 대한 비유입니다 (p.21~22).

컨텍스트를 "점점 길어지는 프롬프트"가 아니라 진화하는 플레이북(식별자가 달린 bullet 모음)으로 다룹니다. Generator가 bullet을 참조해 과제 궤적을 만들고, Reflector가 성공·실패 궤적에서 통찰을 증류하고, Curator가 항목 단위로 플레이북을 갱신합니다. 이전 메모리 시스템의 두 한계, 즉 반복 재작성으로 과거 정보가 유실되는 Context Collapse와 LLM이 지나치게 간결한 지시를 선호해 세부를 빠뜨리는 Brevity Bias를, 전체 재작성 대신 변경분만 생성하는 Delta Update로 해결합니다. 단, 갱신 규칙과 워크플로우는 여전히 사람이 설계합니다.

오답노트를 매번 처음부터 다시 쓰면 예전에 적어둔 중요한 팁이 사라져요(붕괴). 그래서 ACE는 "오늘 새로 배운 것 한 줄만 추가"하는 방식으로 노트를 키워요. Git에서 파일 전체를 다시 올리지 않고 바뀐 줄만 올리는 것과 같아요.

CONCEPT 05 · p.23–25, 28

MCE (Meta Context Engineering)와 Meta-Harness

요약본의 "MCE: 컨텍스트 내용(C) 최적화와 검색 방식(BM25·임베딩·하이브리드) 최적화를 교차 반복"은 슬라이드 텍스트와 다릅니다. MCE(Ye et al. 2026)의 핵심은 메커니즘(스킬)과 산출물(컨텍스트)의 분리이며, Meta-Agent가 스킬을 진화시키고 Base-Agent가 그 스킬로 컨텍스트를 구성합니다. BM25/임베딩 언급은 텍스트에 없습니다 (p.23~24).

MCE는 "컨텍스트를 어떻게 관리할지"(메커니즘)와 "무엇을 담을지"(내용)를 분리합니다. Meta-Agent가 Agentic Crossover → Skill Generation으로 컨텍스트 엔지니어링 방법 자체(학습 절차, 에러 분석 코드, 템플릿, 검증, 검색·필터링 같은 동적 연산자)를 자유 형식 스킬로 진화시키고, Base-Agent는 그 스킬을 실행해 과제별 컨텍스트를 만듭니다. ACE처럼 휴리스틱을 강제하지 않고 스킬과 컨텍스트를 공진화시킵니다. Meta-Harness(Lee et al. 2026)는 한 단계 더 내려가 "무엇을 저장·검색·제시할지 결정하는 코드" 자체를 최적화하는 하네스를 최적화하는 하네스입니다. 제안자는 코딩 에이전트이고 출력은 비용 대 성능의 파레토 프론티어 위 하네스 후보 집합입니다. ADAS와의 차이는 전체 실행 이력에 선택적 접근, 에이전틱 진단, 최소한의 외부 루프 세 가지입니다.

ACE가 "오답노트 잘 쓰는 법"을 사람이 정해줬다면, MCE는 "오답노트 쓰는 법 자체"를 AI가 실험하며 바꾸게 해요. Meta-Harness는 거기서 더 나아가 "공부 도구를 만드는 공장"을 AI가 짓는 것이고, 비용 대비 성적이 가장 좋은 도구들만 남겨요.

CONCEPT 06 · p.26–29

워크플로우 디자인: AI Scientist · Autodata agent · ADAS · AFlow

요약본의 "AutoDataAgent: 제미나이(출제)·GPT(검증)·Qwen(학습)"에서 모델명은 슬라이드 텍스트에 없습니다. 실제 구성은 Challenger / Weak Solver / Strong Solver / Verifier(Judge)입니다. 또 "ADAS, AFlow — MCTS 기반"은 부정확합니다. MCTS는 AFlow의 방법이고, ADAS는 meta-agent search입니다 (p.27~29).

수작업 워크플로우로는 AI Scientist(아이디어 → 코드 → 실험 → 분석 → 원고 → 피어리뷰)와 모든 주장을 근거에 추적하는 ScientistOne(Chain-of-Evidence)이 있습니다. Autodata agent는 Challenger가 문제를 제안하고, Weak Solver가 "충분히 어려운지", Strong Solver가 "여전히 풀리는지"를 검사해 딱 맞는 난이도의 데이터를 합성합니다. 설계 공간이 거대하므로 워크플로우 설계를 탐색 문제로 봅니다. ADAS는 메타 에이전트가 새 워크플로우를 제안하는 meta-agent search이고, AFlow는 워크플로우를 그래프(노드 = LLM 호출, 엣지 = 코드 논리)로 표현해 MCTS로 최적화합니다. 점수와 균등 탐색의 soft mixture로 노드를 고르고, LLM이 수정안을 내고, 실행·평가해 개선되면 트리에 추가하며, top-k 평균이 정체되거나 예산이 소진되면 멈춥니다.

큰 문제를 작은 문제로 쪼개 각각 풀고 합치는 "일하는 순서도"를 만드는 건데, 사람이 그리는 대신 AI가 여러 순서도를 그려보고(ADAS), 바둑 AI처럼 나무 모양으로 가지를 뻗어가며 제일 좋은 순서도를 찾아요(AFlow). Autodata는 "너무 쉽지도 어렵지도 않은 문제집"을 자동으로 만드는 출제 위원회예요.

CONCEPT 07 · p.31–38

자기개선 하네스: STOP → Lin et al. → Self-Harness → AHE

STOP(Self-Taught Optimizer, 2023)은 Improver가 자기 코드를 개선하는 초기 사례인데, 경고 결과가 중요합니다. GPT-4에서는 반복마다 성능이 올랐지만 GPT-3.5·Mixtral 같은 약한 모델에서는 오히려 떨어졌습니다. 재귀 구조만으로는 부족하고 베이스 모델이 유능해야 합니다. Lin et al. (2026)은 하네스 편집을 만드는 능력(harness-updating)은 모델 급에 따라 평평하지만, 갱신된 하네스를 활용하는 능력(harness-benefit)은 비단조적이어서 중간 티어 모델이 가장 이득을 본다고 보고했습니다. Self-Harness는 같은 모델이 Weakness mining(실패 패턴 클러스터링) → Harness proposal(bounded edit) → Proposal validation(검증·머지) 루프로 자기 하네스를 고칩니다. 교수님의 우려: 프로그램이 OS를 편집할 수 있으면 추상화 경계가 깨지므로 편집 가능 표면을 설계하고 권한·보안 계층은 루프 밖에 두어야 합니다. AHE(Agentic Harness Engineering)는 병목을 관측가능성으로 보고 3기둥을 둡니다. ① Component(모든 편집 가능 컴포넌트를 파일시스템에 표현), ② Experience(대량 궤적을 증거·실패 패턴으로 요약), ③ Decision(모든 편집에 다음 라운드 예측을 짝지어 검증). Terminal-Bench-2에서 인간 설계 하네스를 넘었고, 진화를 멈춘 하네스가 SWE-bench Verified로 전이됐습니다.

"공부법을 스스로 고치는 학생"인데, 똑똑한 학생은 고칠수록 성적이 오르고 기초가 약한 학생은 오히려 망쳐요(STOP). Self-Harness는 "내가 자주 틀리는 유형"을 모아 공부법을 조금씩 고치고 효과 있는 것만 채택해요. AHE는 "뭘 바꿨는지, 왜 틀렸는지, 바꾼 게 정말 효과 있었는지"를 전부 기록해 두는 게 핵심이에요.

CONCEPT 08 · p.39–46

진화 탐색 계열: GEPA · AlphaEvolve · ShinkaEvolve · DGM · Hyperagents

진화 탐색은 해 집단을 변이시키고 적합도 높은 것만 남깁니다. 탐색 공간이 넓고 그래디언트로 최적화하기 어렵지만 평가는 쉬울 때 적합해서 하네스 탐색에 딱 맞습니다. 프롬프트 영역에는 변이 프롬프트까지 진화시키는 Promptbreeder, 시행착오 궤적에 대한 자연어 반성으로 갱신안을 내는 GEPA가 있습니다. AlphaEvolve는 고정 LLM에게 diff를 만들게 하고 MAP-Elites + Island 진화로 다양성을 유지하며 EVOLVE-BLOCK으로 진화 영역을 명시합니다(파라미터는 갱신 안 함). ThetaEvolve는 여기에 GRPO로 파라미터 갱신을, DemoEvolve는 인간 전문가 시연을 아카이브에 더합니다. ShinkaEvolve는 Adaptive Parent Sampling, Novelty Rejection Sampling, UCB 밴딧으로 LLM을 고르는 식으로 샘플 효율을 높입니다. DGM(Darwin Gödel Machine)은 코딩 에이전트가 자기 코드베이스를 수정해 더 나은 코딩 에이전트가 되고, Hyperagents(DGM-H)는 Task Agent와 Meta Agent를 분리해 Meta Agent가 자기 개선 절차까지 수정합니다(Metacognitive Self-Modification). 구분: Meta-Harness = 에이전트 개선, Hyperagents = 에이전트 + 개선 방법까지.

생물 진화처럼 "여러 버전을 만들고 → 시험 보고 → 잘한 것만 남기고 → 또 변형"을 반복해요. AlphaEvolve는 "프로그램"을 진화시키고, DGM은 "프로그램을 만드는 로봇"을 진화시키고, Hyperagents는 "로봇을 고치는 방법"까지 진화시켜요. ShinkaEvolve는 같은 시도를 두 번 안 하게 해서 시험 횟수를 아껴요.

CONCEPT 09 · p.47–50

가중치 공동 최적화: SIA · Continual Harness

하네스 진화는 비파라메트릭 시스템만 바꾸므로, 완전한 자기개선을 위해선 가중치 갱신도 함께 허용할 수 있습니다. SIA는 Meta-Agent(초기 하네스 제안) + Task-Specific Agent(과제 실행) + Feedback-Agent(최근 궤적을 보고 하네스를 갱신할지 가중치를 갱신할지 선택)로 구성됩니다. Continual Harness는 환경 리셋 없이 실행 중에 둘 다 개선합니다. PRM 기반 평가로 실패 지점을 찾고 → 교사 모델(Gemini 3.1 Pro)이 저점수 스텝의 개선 행동을 생성하고 → 교정 궤적으로 학생 가중치를 SFT하고 → Refiner가 프롬프트·스킬·서브에이전트·메모리를 갱신합니다. 루프 한 바퀴는 현재 모델로 256스텝 실행 → PRM 평가 → 저점수 윈도우 교정 → Soft SFT입니다.

지금까지는 "공부법(하네스)"만 고쳤는데, 이제는 "머리(가중치)"도 같이 고쳐요. SIA는 매번 "이번엔 공부법을 바꿀까, 머리를 훈련할까"를 코치가 고르고, Continual Harness는 선생님이 틀린 단계만 고쳐준 답안으로 다시 공부하면서 동시에 공부법도 손봐요.

CONCEPT 10 · p.51–53

미래 과제: 자동 연구의 6가지 실패 모드와 RSI 병목 7가지

논문 생산 ≠ 과학적 발견. Trehan & Chopra(2026)의 6가지 실패: ① 학습 데이터 기본값 편향(옛 라이브러리), ② 실행 압박 하 구현 표류, ③ 메모리·컨텍스트 저하, ④ 과도한 낙관(Bubeck et al. 2025의 p-hacking: 100번 중 1번 성공만 보고, eureka-ing: 버그로 100%가 나왔는데 돌파구라 착각, numerical duct tape: 수치 불안정을 근거 없는 근사로 덮기), ⑤ 도메인 암묵지 부족, ⑥ 약한 과학적 취향. RSI 병목 7가지: ① 약하고 모호한 평가자, ② 컨텍스트·메모리 생명주기, ③ 부정적 결과의 보존(문헌이 성공 편향이라 LLM이 가설 포기에 약함), ④ 다양성 붕괴, ⑤ 보상 해킹(테스트 과적합, judge 꼼수, 아티팩트 착취 → 평가자와 권한 제어는 루프 밖에, held-out 테스트·트레이스 감사·인간 리뷰), ⑥ 장기 성공(유지보수성·하위 호환은 샌드박스가 못 잡음), ⑦ 인간의 역할(제거가 아니라 스택 위로 이동).

AI가 스스로 공부하다 생기는 흔한 실수들: 시험 100번 봐서 제일 잘 본 1번만 자랑하기(p-hacking), 채점기 버그로 100점 나온 걸 진짜 실력이라 믿기(eureka-ing), 점수만 올리려고 채점기의 허점을 파고들기(보상 해킹). 그래서 채점자는 학생 손이 닿지 않는 곳에 둬야 하고, 어른이 중요한 순간엔 꼭 확인해야 해요.

CONCEPT 11 · p.54–66

HDA (Harness-Delta Attribution): Δ = E − B = O + T + G

요약본의 "약 90%가 오버피팅"은 ALFWorld에서 98%가 정확합니다. 벤치마크마다 다르며 CREATE는 T 지배, SWE-bench Verified는 G가 뚜렷합니다. "ARC-AGI-3", "60%→90%" 수치와 O 측정 예시 "객관식 정답은 3번"은 슬라이드 텍스트에 없습니다(실제 사례는 LiveMath의 "a stronger result can be proven" 선택지가 35문항 중 21문항에서 항상 정답). 출처 확인 전까지 발표에서는 쓰지 않는 것이 안전합니다 (p.58, 61, 63~64).

하네스 진화는 고정 모델 주변의 비파라메트릭 시스템을 과제 피드백으로 반복 갱신하는 텍스트 공간 최적화입니다. 총점 상승은 메커니즘을 숨기므로 이득 Δ를 셋으로 분해합니다. O(Overfitting): 최적화 설정 특유의 패턴에 의존해 분포 이동 시 사라지는 이득(데이터셋 아티팩트 착취, proposer의 지식 증류, executor를 안 부르는 결정적 코드). T(Test-Time Scaling): 재시도·검증·병렬 샘플링으로 추론 계산을 더 써서 얻는 이득. G(Generalizable Improvement): 나머지, 재사용 가능한 스킬과 더 나은 과제 분해. 측정 장치는 네 개입니다. B 베이스 하네스, E 진화 하네스, B_cc B를 E와 같은 호출 횟수로 실행한 것, E_neutral E에서 의심되는 오버피팅 특성을 제거한 사본. 따라서 T ≈ B_cc − B, O ≈ E − E_neutral, G = Δ − O − T 이고 O는 암묵적 오버피팅을 다 못 잡으므로 하한입니다. 결과: ALFWorld는 5개 모델 모두 학습 성공률 100%에 도달했지만 이득의 98%가 O. LiveMath는 데이터셋 지름길. CREATE는 call-matched 베이스라인이 Claude Haiku 4.5 이득의 49%를 회복했고 Qwen3.6-35B-A3B에서는 진화 하네스를 능가. SWE-bench Verified는 가장 충실하지만 주로 약한 executor에서. 16개 설정 중 4개는 held-out에서 베이스라인보다 나빴습니다.

새 공부법으로 성적이 60→90점이 됐다고 쳐요. 그 30점이 어디서 왔는지 셋으로 쪼개요. "답지에 특정 패턴이 많다는 걸 외운 것"(O, 다른 시험에선 소용없음), "시험을 다섯 번 보고 제일 잘 본 걸 낸 것"(T, 시간을 더 쓴 것뿐), "진짜 개념을 이해한 것"(G). 꼼수 규칙을 지우고 시험 횟수를 똑같이 맞춰 보면 진짜 실력(G)만 남아요. 연구 결과, 어떤 과목에선 30점 중 29점이 "답지 외우기"였어요.

CONCEPT 12 · p.67–92

에이전트 평가(evals) 기초: Anthropic "Demystifying evals for AI agents"

요약본의 "TAU-bench 계열 라벨 오류 약 30%"는 슬라이드 텍스트에 없습니다. 슬라이드에 있는 것은 Opus 4.5의 τ²-bench 항공권 사례(유효한 해법을 벤치마크가 실패 처리), "pass@100 = 0%면 과제가 깨진 신호", "transcript를 읽어라"입니다 (p.69, 86, 88).

용어: task(입력 + 성공 기준), trial(한 번의 시도, 출력이 변동하므로 여러 번), grader(채점 로직, task당 여럿), transcript(출력·툴 호출·추론·중간 결과 전체 기록), outcome(trial 종료 시 환경의 최종 상태. "예약했습니다"라는 말이 아니라 DB에 예약이 있는지), evaluation harness(eval을 돌리는 인프라) vs agent harness(모델을 에이전트로 만드는 시스템. Claude Code가 그 예이고 Agent SDK로 같은 원시 요소를 씀), suite vs benchmark. 정적 eval의 한계: Opus 4.5가 τ²-bench 항공권 문제에서 "Basic Economy는 변경 불가, Economy 업그레이드는 가능" 정책의 허점을 찾아 업그레이드 후 날짜를 변경했는데, 벤치마크는 거절을 기대해 실패 처리했습니다. 실제로는 더 나은 유효 해법이었죠. Grader는 code-based / model-based / human 세 종류. Capability eval(낮은 pass rate에서 시작, 오를 언덕) vs Regression eval(~100% 유지, 퇴행 방지). 0→1 로드맵 8단계: 실제 실패에서 20~50개 과제로 시작 → 수동 테스트하던 것부터 → 전문가 둘이 같은 판정을 내릴 명확한 과제(프론티어 모델에서 pass@100 = 0%면 대개 과제가 망가진 신호) → 균형 잡힌 집합 → 안정적 환경 → grader 신중 설계 → transcript를 읽어라 → 포화 모니터링 → 열린 기여. 자동 감사 도구 Petri도 공개됐습니다.

AI 비서가 잘하는지 재는 "시험지 만들기"예요. 시험지는 문제(task), 여러 번 풀기(trial), 채점 기준(grader), 풀이 과정 기록(transcript), 실제 결과(outcome. "예약했어요"라고 말한 게 아니라 진짜 예약됐는지)로 이루어져요. 재밌는 사례: Claude가 항공권 규정의 빈틈을 찾아 더 좋은 답을 냈는데 시험지는 "틀림"이라 했어요. 시험지도 틀릴 수 있으니 풀이 기록을 꼭 읽어봐야 해요.

하네스 진화로 점수가 B에서 E로 올랐습니다. 토글을 하나씩 켜면서 그 이득이 오버피팅(O, 답지 외우기) · 테스트타임 스케일링(T, 시험 여러 번 보기) · 진짜 개선(G, 실력)으로 쪼개지는 걸 보세요. 프리셋 숫자는 슬라이드 기반 예시 수치입니다.

B 베이스 G 진짜 개선 (실력) T 테스트타임 (시험 여러 번) O 오버피팅 (답지 외우기) Δ 아직 분해 안 됨

측정 정의: T = B_cc − B (같은 호출 예산을 준 베이스라인의 향상), O = E − E_neutral (오버피팅 특성을 제거했을 때 사라지는 몫, 하한), G = Δ − O − T. held-out에서는 O가 사라지고 G가 음수면 베이스보다 못합니다(논문의 16개 설정 중 4개). 호출 횟수를 1로 두면 T는 0이 됩니다.

예상 문제

Q1. Δ = E − B를 세 메커니즘으로 분해할 때 B_cc와 E_neutral이 각각 무엇을 통제하는지 설명하고, 오버피팅 추정치가 왜 "하한"인지 쓰라.
B_cc는 베이스 하네스를 진화 하네스와 같은 모델 호출 횟수(추론 예산)로 실행한 것으로, B_cc − B가 테스트타임 스케일링(T)을 측정한다. E_neutral은 진화 하네스에서 하드코딩 규칙 등 의심되는 오버피팅 특성을 제거·중화한 사본으로, E − E_neutral이 오버피팅(O)을 측정한다. G = Δ − O − T. 오버피팅 중 일부는 암묵적이거나 다른 메커니즘과 얽혀 있어 탐지·제거되지 않을 수 있으므로 측정된 O는 필연적으로 하한이다.
Q2. ACE가 Context Collapse와 Brevity Bias를 어떻게 해결하는지 세 구성요소와 함께 설명하고, MCE가 ACE와 달라지는 핵심을 한 문장으로 쓰라.
Generator가 플레이북 bullet을 참조해 궤적을 생성하고, Reflector가 성공/실패 궤적에서 통찰을 증류하며, Curator가 증분적·항목화된 델타 업데이트로 플레이북을 갱신한다. 전체 재작성/요약을 하지 않으므로 반복 재작성에 의한 정보 유실(Context Collapse)과 과도한 간결화(Brevity Bias)를 피한다. MCE는 "어떻게 관리할지(메커니즘 = 스킬)"와 "무엇을 담을지(내용)"를 분리해, 휴리스틱을 강제하는 대신 Meta-Agent가 스킬을 진화시키고 Base-Agent가 그 스킬로 컨텍스트를 구성하도록 공진화시킨다.
Q3. (객관식) AFlow의 워크플로우 최적화 방식으로 옳은 것은? ① 메타 에이전트가 새 설계를 제안하는 meta-agent search ② 워크플로우를 그래프로 표현하고 MCTS로 탐색 ③ 코딩 에이전트가 자기 코드베이스를 수정해 아카이브에 저장 ④ 후보 프로그램 풀에 MAP-Elites와 island 진화 적용
②. ①은 ADAS, ③은 DGM, ④는 AlphaEvolve.
Q4. STOP의 "경고 결과"와 Lin et al.의 harness-benefit 비단조성을 근거로 "하네스 개선과 모델 지능의 관계"에 대한 결론을 설명하라.
STOP은 GPT-4에서는 반복마다 성능이 개선됐지만 GPT-3.5·Mixtral 같은 약한 모델에서는 저하됐다. 재귀 구조만으로는 부족하고 베이스 모델이 메커니즘을 개선할 만큼 유능해야 한다. Lin et al.은 하네스 편집 생산 능력(updating)은 모델 급에 따라 평평하지만, 갱신된 하네스를 활용하는 능력(benefit)은 비단조적으로 중간 티어가 가장 이득을 본다고 보고했다. 결론: 하네스 엔지니어링은 더 나은 "배포"를 가능하게 하지만 핵심은 여전히 지능이며, 장기적으로 많은 하네스 개선이 모델 행동으로 내재화되더라도 외부 컨텍스트·툴과의 인터페이스(목표·제약·평가 명세)는 남는다.
Q5. (a) transcript와 outcome의 차이, (b) capability eval과 regression eval의 차이, (c) 프론티어 모델에서 pass@100 = 0%의 의미를 설명하고, Opus 4.5 τ²-bench 사례가 왜 "transcript를 읽어라"와 연결되는지 쓰라.
(a) transcript는 trial 전체 기록(출력·툴 호출·추론·중간 결과), outcome은 trial 종료 시 환경의 최종 상태(예: "예약했다"는 말이 아니라 DB에 예약 레코드 존재 여부). (b) capability eval은 낮은 pass rate로 시작해 오를 언덕을 주고, regression eval은 ~100%를 유지해 퇴행을 잡는다. (c) 많은 trial에 걸쳐 0% 통과는 대개 에이전트가 무능한 게 아니라 과제 명세나 grader가 망가졌다는 신호다. Opus 4.5는 정책상 유효한 해법(Economy 업그레이드 후 날짜 변경)을 찾았지만 벤치마크는 거절을 기대해 실패 처리했다. grader가 유효한 해법을 거부했는지 진짜 실수였는지는 transcript를 읽어야만 알 수 있고, 실패는 "공정해 보여야" 한다.
